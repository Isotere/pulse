# Рабочие промпты Pulse

Этот файл содержит короткие запросы для типовых сессий Codex, запущенных из корня Pulse. Правила из `AGENTS.md` действуют всегда; промпт задаёт конкретную задачу и разрешённые действия.

Текст в угловых скобках нужно заменить своими данными. Если Codex должен изменить файлы, GitHub или vault, это следует написать прямо. Запросы «проверь», «объясни», «спланируй» и «проведи ревью» не разрешают вносить исправления.

## 1. Начать рабочую сессию

```text
Проверь текущее состояние Pulse.

1. Прочитай AGENTS.md.
2. Покажи текущую ветку и состояние рабочего дерева.
3. Если ветка связана с GitHub Issue, прочитай задачу.
4. Кратко перечисли уже имеющиеся артефакты и ближайший проверяемый результат.

Ничего не изменяй, не создавай ветки и не обращайся к отдалённым этапам.
```

## 2. Разобрать тему Rust

```text
Объясни тему Rust: <тема>.

Контекст: <где тема встретилась в Pulse или курсе>.
Что я уже понимаю: <текущие знания>.

Раскрой:
1. какую проблему решает механизм;
2. как он работает на уровне, достаточном для моей задачи;
3. чем отличается от ближайшего аналога в Go;
4. какие ошибки здесь типичны;
5. как проверить понимание на небольшой самостоятельной практике.

Не решай задачу за меня. Небольшой изолированный пример допустим только для объяснения механизма.
```

## 3. Получить одну подсказку

```text
Я решаю задачу самостоятельно и застрял.

Задача: <описание>.
Что уже сделал: <действия>.
Что ожидал: <результат>.
Что получил: <результат или ошибка>.

Дай только одну следующую подсказку. Не пиши код и не раскрывай полное решение. Если данных недостаточно, задай один конкретный вопрос.
```

## 4. Разобрать ошибку компилятора

```text
Помоги понять ошибку компилятора Rust.

Команда: <команда>.
Сообщение компилятора:
<полный текст>

Связанные файлы: <пути>.

Объясни первопричину, нарушенное правило Rust и вторичные сообщения. Затем назови возможные направления исправления и их компромиссы.

Не изменяй файлы и не пиши исправленный код: сначала я попробую исправить ошибку сам.
```

## 5. Выделить следующую задачу этапа

```text
Используй $pulse-stage-plan.

Помоги выделить следующую небольшую задачу текущего этапа Pulse.

Текущее состояние: <что уже готово>.
Ближайший результат этапа: <результат>.
Доступное время: <часы или занятия>.
Изученные темы Rust: <темы>.

Задача должна иметь один наблюдаемый результат, понятные входы, границы и критерии завершения. Не добавляй скрытую подготовительную работу и не описывай реализацию.

Пока ничего не изменяй в репозитории и vault.
```

## 6. Детализировать этап

```text
Используй $pulse-stage-plan.

Детализируй этап Pulse: <номер и название>.

Прочитай описание проекта, верхнеуровневые этапы, организацию монорепозитория и фактический результат предыдущего этапа.

Опиши исходную точку, назначение, входы, границы, ожидаемые результаты, последовательность работы, риски и критерии завершения. Разбей этап на задачи, выполнимые одним человеком за разумное время.

Обнови документ этапа в vault. Не создавай GitHub Issues и не переходи к реализации.
```

## 7. Проверить завершение задачи или этапа

```text
Используй $pulse-stage-plan.

Проверь завершение <задачи или этапа>.

Критерии: <критерии или путь к документу>.
Полученный результат: <файлы, команды, тесты и наблюдения>.
Известные ограничения: <ограничения>.

Сопоставь критерии с подтверждённым результатом. Верни одно решение:
- завершено;
- не завершено: назови конкретный недостающий результат;
- критерий больше не нужен: объясни причину.

Не изменяй файлы.
```

## 8. Создать учебный конспект

```text
Используй $pulse-learning-note.

Создай или обнови конспект по теме: <тема>.

Источник: <курс, глава, документация или мои заметки>.
Раздел материалов: <Rust, Консоль и VIM, финансы и инвестиции>.
Что нужно раскрыть: <вопросы>.

Сначала проверь существующие конспекты, чтобы не дублировать материал. Отдели содержание источника от дополнительных пояснений. Для версионно-зависимых сведений используй актуальную официальную документацию.

Обнови соответствующий файл в vault. Код Pulse не изменяй.
```

## 9. Обновить документацию или результат этапа в vault

```text
Используй $pulse-vault-docs.

Обнови документацию Pulse в vault.

Целевой документ: <путь>.
Что произошло: <подтверждённые факты>.
Доказательства: <файлы, commits, команды, тесты или наблюдения>.
Известные ограничения: <ограничения>.

Зафиксируй только подтверждённый результат. Не выдавай планы за выполненную работу. Проверь согласованность терминов и при необходимости обнови словарь.

Репозиторий не изменяй.
```

## 10. Провести ревью локальных изменений

```text
Используй $pulse-code-review.

Проведи ревью <рабочего дерева, staged diff или текущей ветки>.

Связанная задача: <номер issue или описание>.
Критерии готовности: <критерии>.

Проверь корректность, обработку ошибок, тесты, границы ответственности, идиоматичность Rust и предметные инварианты Pulse. Сначала перечисли замечания по убыванию серьёзности с указанием файла и строки.

Не изменяй файлы и не отправляй review в GitHub.
```

## 11. Создать ветку для GitHub Issue

```text
Используй $pulse-github-flow.

Создай связанную рабочую ветку для issue № <номер>.

1. Проверь рабочее дерево и прочитай issue.
2. Используй master как base.
3. Создай ветку через gh issue develop по соглашению issue-<номер>-<краткое-название>.
4. Переключись на неё и покажи итоговый статус.

Не изменяй код, статус issue, итерацию или поля GitHub Project.
```

## 12. Подготовить pull request

```text
Используй $pulse-github-flow.

Создай pull request из текущей ветки для issue № <номер>.

Проверь diff, commits и относящиеся к задаче проверки. Если рабочее дерево содержит незакоммиченные изменения или проверки не проходят, остановись и сообщи причину: ничего не исправляй и не создавай commit самостоятельно.

Если ветка готова, отправь её в origin и создай PR в master. В описании укажи результат, выполненные проверки, известные ограничения и Closes #<номер>.

Не выполняй merge и не закрывай issue вручную.
```

## 13. Диагностировать сбой CI

```text
Диагностируй сбой GitHub Actions для <PR или run ID>.

Прочитай конфигурацию workflow и логи упавших jobs. Отдели первичную ошибку от последующих сбоев. Составь гипотезы по убыванию вероятности и для каждой предложи минимальную проверку.

Не запускай workflow повторно, не меняй файлы и не предлагай исправление, пока причина не подтверждена.
```

## 14. Прямо поручить реализацию Codex

Этот промпт нужен только тогда, когда код или конфигурацию следует написать Codex.

```text
Реализуй изменение: <точное описание>.

Связанная issue: <номер>.
Разрешённая область изменений: <файлы или каталоги>.
Не изменять: <ограничения>.
Критерии готовности: <проверяемые критерии>.

Перед изменением прочитай AGENTS.md, задачу и существующие соглашения. Не выполняй побочные рефакторинги и не добавляй возможности сверх задачи.

После изменения запусти относящиеся к задаче проверки. Не создавай commit, push или PR без отдельного запроса. Перечисли изменённые файлы, подтверждённое поведение и оставшиеся ограничения.
```
