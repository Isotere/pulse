# Ревью Pulse

Ревью отделено от реализации. Не меняй файлы, не создавай commits и не отправляй GitHub review без прямого запроса.

## Порядок работы

1. Уточни объект ревью из запроса: рабочее дерево, staged diff, commit, ветка или PR.
2. Прочитай связанные issue, описание этапа и изменённые файлы. Не загружай несвязанные материалы.
3. Изучи diff в контексте вызывающего кода, тестов и публичных контрактов.
4. Запусти относящиеся к изменению проверки, если они доступны. Диагностическая команда не разрешает исправлять её результат.
5. Сопоставь поведение с критериями issue или этапа.

## На что смотреть

В первую очередь ищи:

- ошибки корректности и регрессии;
- потерю или неверное преобразование данных;
- недетерминированность результата;
- использование будущей информации в историческом эксперименте;
- смешение фактических, синтетических и модельных событий;
- ошибочную трактовку неизвестного состояния;
- нарушения обработки ошибок и восстановления;
- проблемы владения, времени жизни и конкурентного доступа;
- необоснованный `unsafe` и недокументированные инварианты;
- несовместимость публичного API;
- отсутствующие тесты для изменённого поведения.

Не требуй абстракций, patterns или разбиения на crates без конкретной проблемы. Не выдавай вкусовое предпочтение за дефект.

## Формат результата

Сначала перечисли замечания по убыванию серьёзности. Для каждого укажи:

- файл и строку;
- наблюдаемую проблему;
- возможное последствие;
- направление исправления без готового кода, если пользователь его не просил.

После замечаний перечисли открытые вопросы и выполненные проверки. Если существенных проблем нет, скажи это прямо и укажи, что не удалось проверить.

Отправляй комментарий или решение review в GitHub только по прямому запросу пользователя.
